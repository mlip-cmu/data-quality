# Data Card: Supermarket inventory dataset (synthetic)

## The dataset creator and purpose

- **Created by** the course staff for the lecture "Data Quality" (Machine Learning in
  Production). Generated by the `inventory-data` package in this repository; version 2.
- **Purpose**: teaching. It supports the forecasting model of a supermarket chain that
  predicts future sales per store and product to decide what to restock, when, and how many.
- **Not for**: any real business decision. All stores, suppliers, people, and numbers are
  invented. ZIP codes and city names are real, the stores are not.

## How to use the dataset

```python
import inventory_data as d
d.sales()               # daily sales per store and product (clean)
d.deliveries(dirty=True) # the same table with realistic entry errors
d.errors()              # ground truth of every injected error
```

- Use the **clean** tables to train and evaluate models; use the **dirty** tables and
  `errors()` to evaluate data validation and cleaning; use the **drift** tables
  (`drift_*()`) to evaluate monitoring.
- The tables `truth` and `drift_truth` contain values that a real chain cannot observe (true
  demand, lost sales, unrecorded shrinkage). Use them only to score methods.

## Data fields

| Table | Field | Meaning | Unit / values |
|---|---|---|---|
| products | `gtin` | Global Trade Item Number | 13 digits, **text** (leading zero) |
| products | `unit` | unit of `quantity` everywhere | `count`, `kg`, `liter` (refill station) |
| products | `unit_price` | regular price per unit | USD |
| products | `case_length_cm` … | size of one supplier case | cm (not inches) |
| products | `case_pack` | units per case | count |
| sales | `quantity` | **recorded** sales per store, product, and day | the product's `unit` |
| sales | `unit_price`, `promo` | price paid; promotion = 20 % off | USD, bool |
| deliveries | `received_at`, `entered_at` | when the goods arrived, when the clerk typed them in | local time |
| stock_counts | `counted_qty` | weekly manual count (Sundays) | the product's `unit` |
| weather | `temp_c` | daily mean temperature per weather station | °C (see drift) |
| oos_reports | `reported_at` | a customer reported an empty shelf in the app | local time |

## Datapoint example

```json
{"date": "2025-03-14", "store_id": 1, "product_id": 101, "quantity": 38.96,
 "unit_price": 1.19, "promo": true, "revenue": 46.36}
```

Product 101 is "Banana", sold by kg, on promotion (1.49 → 1.19 USD); the store is "Oakland"
in Pittsburgh (15213).

## Data source and collection

| Source | How it is collected | Reliability |
|---|---|---|
| POS system | every sale at the checkout; weighed items use the checkout scales | high, but scales can drift |
| Product master data | typed in by staff when a product is listed | low: typos, units, swapped fields |
| Delivery receipts | typed in by the receiving clerk, sometimes days later | medium: duplicates, forgotten receipts |
| Stock counts | weekly manual count | medium: miscounts, transposed digits |
| Weather | external weather API | high, but the provider can change the format |
| Customer app | crowdsourced "shelf empty" reports | low: incomplete and noisy |

## Labeling process

There is no manual labeling. The label of the forecasting model is the **recorded sales**,
which is a proxy for demand: on a day with a stock-out, the sales show how much was on the
shelf, not how much customers wanted (censored). Stock-outs happen more often for seasonal
products (tomato soup in winter, ice cream in heatwaves). The customer app reports only a
small part of the stock-outs.

## Data quality

- **Noise**: daily demand varies randomly; checkout scales add about 1 % noise per reading;
  manual stock counts are off by 1–3 units in about 10 % of the counts.
- **Drift**: the clean data is stable (2024–2025). The drift scenario documents seven events
  with dates (fad diet, drifting scales, competitor, new stores in Florida, heatwave, POS in
  lb, weather API in °F). The world after 2025 is unknown.
- **Biases**: the chain has only urban and suburban stores in PA and OH before 2025; a model
  trained on it does not know other climates or regions (see the Florida stores).
- **Curation**: products are fixed (60); there are no new products or delistings; prices do
  not change except for promotions. These are simplifications, not properties of real data.

## Maintenance

Regenerate with `uv run inventory-data --force`. A change of the generator must bump
`VERSION` in `inventory_data/__init__.py` and update this card (`uv run datacard_stats.py`).
